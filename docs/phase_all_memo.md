# 전체 로드맵

## 0단계: 이전 기준과 범위 확정

아직 Bevy 코드를 작성하지 않고, Unity판을 정답 자료로 정리한다.

작업:

- 현재 클라이언트 `v1.0.3`을 기준 버전으로 지정
- 구현된 기능과 미완성 기능 구분
- 기존 버그 중 이식할 것과 고칠 것 구분
- JSON 맵 포맷 문서화
- 전체 블록과 옵션 목록 작성
- 서버 API 목록과 요청·응답 형식 문서화
- 대표 테스트 맵 선정
- Unity 물리 설정과 게임 상수 기록

대표 물리 테스트 맵도 준비

- 평지 연속 바운스
- 벽·천장 충돌
- 경사·곡선 블록
- 중력 반전
- 점프·대시·직진
- 텔레포트·포탈
- 이동 블록
- 레이저·거울
- 기어
- 스윙·클론

완료 조건:

- 무엇을 이식해야 하는지 체크리스트로 전부 확인 가능
- JSON과 서버 API 규격이 Unity 코드 없이도 이해 가능

## 1단계: Bevy 프로젝트 기반 구축

Unity 프로젝트는 그대로 두고 별도의 `BB_FME_Bevy` 프로젝트를 만든다.

초기 기술 구성:

- Rust workspace
- Bevy 0.19 고정
- `Cargo.lock` 저장
- PC 개발 빌드 우선
- 로그와 오류 처리
- 기본 설정 파일
- 자동 포매팅과 Clippy
- 최소 단위 테스트
- 빠른 개발 빌드를 위한 linker 설정

이 단계에서 배우는 Bevy 개념:

- `App`
- Entity와 Component
- System과 Schedule
- Resource
- Plugin
- State
- Event 또는 Observer
- Asset Server
- `Update`와 `FixedUpdate` 성격의 스케줄 분리

첫 결과물:

- 창 열기
- 2D 카메라
- 스프라이트 출력
- 키보드·마우스 입력
- 게임 상태 전환
- 로딩 화면

완료 조건:

- PC에서 항상 동일하게 빌드·실행
- 빈 게임 상태와 플레이 상태를 전환 가능

## 2단계: 데이터와 에셋 호환

게임플레이보다 먼저 기존 맵을 읽을 수 있도록 만든다.

추천 모듈 구조:

BB_FME_Bevy/
├─ crates/
│ ├─ bbfme_core 공통 타입과 설정
│ ├─ bbfme_map JSON 맵 로딩·저장
│ ├─ bbfme_game 게임 규칙
│ ├─ bbfme_blocks 블록 구현
│ ├─ bbfme_net 서버 통신
│ └─ bbfme_editor 맵 에디터
└─ app/ 실제 Bevy 실행 프로그램

작업:

- `MapJsonDataInfo`를 Rust `serde` 구조체로 이식
- 기존 맵 JSON 역직렬화
- 다시 JSON으로 저장
- 좌표·방향·블록 옵션 보존 검사
- `block_assets_config.json` 호환
- 기존 PNG와 폰트 로딩
- 블록 이름과 에셋을 연결하는 레지스트리 구현
- 잘못된 맵 데이터 검증기 작성

중요 원칙:

- 기존 블록 ID인 `fb_jump`, `ob_gear` 등을 변경하지 않음
- JSON에 `schema_version`을 추가하더라도 구버전 맵은 계속 읽음
- Rust 내부에서는 타입을 안전하게 사용하되 저장 형식은 호환 유지

완료 조건:

- 기존 JSON 맵을 읽고 동일한 의미로 다시 저장
- 존재하지 않는 블록과 잘못된 옵션을 명확한 오류로 보고

## 3단계: 물리 엔진 검증

기본 후보는 `bevy_rapier2d`입니다. Rapier는 Bevy 2D 통합, CCD, 센서, 충돌 이벤트, contact hook, 디버그 렌더링을 제공한다. [Rapier 문서](https://rapier.rs/docs/user_guides/rust/getting_started_bevy/)

이 단계에서는 물리 엔진을 바로 확정하지 않고 작은 실험을 한다.

실험 대상:

- Rapier
- 필요할 경우 Avian 비교
- 일부 움직임을 자체 물리로 구현하는 혼합 방식

측정할 항목:

- 공의 연속 바운스 안정성
- 벽 모서리 충돌
- 고속 대시 시 관통 여부
- 이동 블록 위 충돌
- 중력 반전
- 모바일 성능
- 구현 복잡도
- 디버깅 편의성

추천 구조:

PhysicsPlugin
├─ BallBody
├─ CollisionLayers
├─ ContactClassification
├─ BounceRules
├─ MovementRules
└─ PhysicsBackend

게임 코드가 Rapier 타입에 직접 강하게 묶이지 않게 구성한다. 그러면 물리 엔진을 교체하더라도 블록과 게임 규칙 전체를 다시 작성하지 않아도 된다.

물리 timestep은 처음부터 고정하지 않고 `60Hz`, `120Hz`, CCD 조합을 비교한다. Unity의 50Hz를 복제할 의무가 없으므로 새 엔진에서 가장 안정적인 값을 선택한다.

완료 조건:

- 10분 이상 연속 바운스해도 불안정하지 않음
- 고속 이동 시 치명적인 블록 관통이 없음
- 물리 엔진 최종 선택 기록 작성

## 4단계: 기본 게임 수직 단면

이제 작은 게임 하나를 완성한다

구현 범위:

- 공 생성
- 좌우 이동
- 바운스
- 카메라 추적
- 일반 블록
- 별
- 가시
- 점프 블록
- 맵 경계
- 사망
- 재시작
- 클리어
- 간단한 타이머
- 키보드·마우스 입력

기존 맵 JSON으로 실행해야 한다. 테스트 전용 하드코딩 맵을 최종 구조로 사용하면 안 된다.

완료 조건:

- Unity에서 만든 기본 맵을 Bevy에서 플레이
- 사망·재시작·클리어까지 한 사이클 완성
- headless 테스트로 일부 게임 규칙 검증

이 지점이 첫 번째 큰 성공 체크포인트.

- 변화 블록

## 6단계: 게임 상태와 테스트 모드

Unity의 많은 `static` 상태를 Bevy Resource와 Component로 재설계한다.

주요 상태:

- 앱 상태
- 현재 게임 모드
- 플레이 세션
- 맵 원본 상태
- 플레이 중 변경 상태
- 사용자 정보
- 선택된 온라인 맵
- 입력 상태
- 타이머·클리어 상태

재시작은 현재 오브젝트를 하나씩 원상 복구하기보다 다음 방식이 안전하다.

MapDefinition
↓ 세션 시작
PlayWorld 생성
↓ 사망·재시작
PlayWorld 제거
↓
MapDefinition에서 다시 생성

완료 조건:

- 같은 맵을 100회 재시작해도 상태 누수 없음
- 에디터 테스트 종료 후 편집 데이터가 정확히 복원됨
- 포탈·레이저·이동 블록도 초기화됨

## 7단계: 맵 에디터 재구현

가장 큰 작업 중 하나이므로 다시 여러 단계로 나눈다.

### 7-A: 기본 편집

- 격자
- 카메라 이동
- 블록 팔레트
- 배치·삭제
- 회전
- 맵 크기 변경

### 7-B: 고급 편집

- 블록 옵션
- 스위치 초기 상태
- 시간 제한
- 타임어택 설정
- 포탈·텔레포트 연결 검증
- 맵 유효성 검사

### 7-C: 사용성 개선

- Undo·Redo
- 선택 영역
- 복사·붙여넣기
- 잘못된 블록 강조
- 저장 전 검사 결과
- 자동 저장 또는 복구 파일

### 7-D: 테스트와 저장

- 즉시 플레이 테스트
- 테스트 종료 후 편집 화면 복귀
- JSON 저장·불러오기
- 썸네일 렌더링
- 서버 저장 슬롯

모바일에서도 사용하는 에디터이므로 런타임 UI는 Bevy UI를 중심으로 구성하는 편이 안전하다. Bevy 0.19에는 텍스트 입력과 에디터용 위젯이 추가됐지만 아직 일부 기능은 초기 단계이므로 필요한 UI를 직접 보완해야 한다. [Bevy 0.19 기능 설명](https://bevy.org/news/bevy-0-19/)

완료 조건:

- Unity 에디터 없이 새 맵 제작 가능
- Bevy에서 만든 맵을 Unity판에서도 읽을 수 있음
- Unity에서 만든 맵을 Bevy 에디터에서 수정 가능

## 8단계: 메뉴·온라인 기능·서버

먼저 서버 없이 Mock 응답으로 UI를 완성하고, 이후 실제 서버를 연결한다.

클라이언트 작업:

- 로딩·메인 메뉴
- 설정 저장
- 로그인·회원가입
- 프로필
- 사용자 맵 목록
- 검색·정렬·페이지네이션
- 맵 상세 정보
- 좋아요·평점·댓글
- 타임어택 기록
- 업데이트 노트
- 네트워크 오류와 오프라인 처리

개선할 점:

- 고정 IP 제거
- 개발·운영 URL을 설정 파일로 분리
- HTTPS 적용
- 요청 timeout
- 공통 오류 형식
- 토큰 기반 사용자 인증
- 사용자 번호나 닉네임만 믿는 요청 제거
- 재시도와 중복 전송 방지

서버는 별도 트랙으로 진행한다.

클라이언트 개발
└─ Mock API 사용

서버 개발
├─ 기존 API 명세 복원
├─ Axum + MySQL 구현
└─ 인증·보안 보강

완료 조건:

- 서버가 꺼져도 게임이 멈추거나 무한 로딩되지 않음
- 온라인 기능 전체 지원
- 기존 사용자 및 맵 DB를 보존할 수 있는 이전 절차 확보

## 9단계: PC·Android 대응

초기에는 PC만 지원하고 게임이 완성된 뒤 Android를 붙인다.

PC:

- Windows 우선
- Linux 개발 빌드
- 해상도·창 모드
- 키보드·마우스·게임패드
- 저장 경로
- 배포 패키지

Android:

- 터치 입력
- 가로 화면
- Safe Area
- 일시 정지·백그라운드 복귀
- 네트워크 권한
- 앱 저장 공간
- DPI와 해상도
- 발열·배터리·메모리
- ARM64 빌드
- APK/AAB
- 서명과 버전 코드

Bevy는 공식 Android 빌드 예제를 제공하지만 `cargo-ndk`와 Gradle 설정이 필요하므로 Unity보다 수작업이 많다. [Bevy 공식 Android 절차](https://github.com/bevyengine/bevy/blob/main/examples/README.md)

완료 조건:

- PC와 Android에서 같은 JSON 맵 실행
- 터치와 키보드의 게임 규칙이 동일
- 중급 모바일 기기에서 안정적인 프레임 유지

- 맵 제작자 대상 베타
- 크래시·성능 수집
- 서버 마이그레이션
- 정식 Bevy 빌드
- Unity 최종 소스와 빌드 보관
- Unity 프로젝트를 읽기 전용 아카이브로 전환
